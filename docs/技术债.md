> 已知但尚未处理的问题清单 —— 目的是"不用通读代码也知道欠了什么"。
> 维护规则：只记事实与状态，不复制实现细节（细节一律给代码路径）；**本文件只放"待修 / 待定"的事**——
> 修完的直接删（历史在 git 里）；确认**不做**的写进对应决策文档（`docs/box-模块规则.md` 的「本插件 v1 的范围」、`DESIGN.md` 的「技术债与已知限制」）后也从这里删。
> 位置一律写「文件 + 符号名」，**不写行号**：行号是位置不是身份，上面随便改几行它就漂了（本项目实际踩过两次）。
> 状态用词：`待定` = 需要用户拍板；`待验证` = 读代码推演得到、尚未用测试确认；`待做` = 已确认、尚未处理。
> 组别即优先级：A 影响用户可见行为 > B 误导读代码的人 > C 可靠性隐患 > D 命名与卫生。
> 对外部系统（box / R / VS Code）的行为断言，标注是**实测**还是**推理** —— 推理被当成定论已经害过两次（模块别名语义、字符串路径）。
